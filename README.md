# Модуль «Учет финансов» — ТигрБанк 🐯💳

## Описание предметной области
Приложение моделирует модуль «Учет финансов» банковского приложения ТигрБанка.
Модуль предназначен для управления личными финансами пользователей и включает:
- учет банковских счетов;
- учет доходов и расходов;
- категоризацию операций;
- финансовую аналитику;
- импорт и экспорт данных в различных форматах.

Приложение реализовано как консольное Java-приложение с использованием
Spring DI-контейнера. Основной акцент сделан на архитектуру и соблюдение
принципов SOLID.

---

## Реализованный функционал

### Основной функционал
- Создание и хранение:
  - банковских счетов (BankAccount);
  - категорий доходов и расходов (Category);
  - операций (Operation).
- Применение операций к счетам с автоматическим пересчетом баланса.

### Аналитика
- Подсчет разницы доходов и расходов за выбранный период.
- Возможность расширения аналитических сценариев без изменения существующего кода.

### Импорт и экспорт данных
- Экспорт данных в форматы:
  - JSON
  - CSV
  - YAML
- Импорт данных из файлов указанных форматов.
- Пользователь может самостоятельно выбрать формат импорта/экспорта.
- Добавление нового формата не требует изменения бизнес-логики.

### Управление данными
- Возможность пересчета баланса счета на основе операций.
- Централизованная работа с хранилищами данных.

### Тестирование
- Модульные тесты для аналитического сервиса (JUnit 5).

## Архитектура приложения

Приложение разделено на логические слои:

- **Domain** — доменная модель и бизнес-сущности.
- **Application** — бизнес-логика и интерфейсы сервисов.
- **Infrastructure** — работа с файлами и хранилищами.
- **Config** — конфигурация Spring DI-контейнера.
- **Console** — пользовательский интерфейс (консоль).

Такое разделение снижает связанность компонентов и упрощает расширение системы.

---

## Использование принципов SOLID

### Single Responsibility Principle (SRP)
- Доменные сущности отвечают только за состояние.
- Сервисы содержат бизнес-логику.
- Импорт/экспорт вынесен в отдельный инфраструктурный модуль.

### Open / Closed Principle (OCP)
- Для добавления нового формата импорта/экспорта достаточно реализовать
  новый сервис, не изменяя существующий код.

### Liskov Substitution Principle (LSP)
- Все реализации репозиториев и сервисов взаимозаменяемы через интерфейсы.

### Interface Segregation Principle (ISP)
- Используются узкоспециализированные интерфейсы сервисов.

### Dependency Inversion Principle (DIP)
- Бизнес-логика зависит от абстракций.
- Все зависимости внедряются через Spring DI-контейнер.

---

## Dependency Injection (Spring)

В проекте используется Spring Core:
- Все сервисы и репозитории регистрируются как бины;
- Внедрение зависимостей осуществляется через конструкторы;
- Это позволяет легко заменить реализации (например, InMemory → БД).

---

## Возможные проблемы при расширении системы
- InMemory-хранилище не подходит для больших объемов данных.
- Консольный интерфейс ограничен по функциональности.
- При росте аналитики потребуется выделение отдельного аналитического модуля.

---

## Почему введенные абстракции улучшают дизайн
- Упрощают тестирование.
- Снижают связанность компонентов.
- Делают систему расширяемой и поддерживаемой.
- Позволяют независимо развивать доменную модель и инфраструктуру.
